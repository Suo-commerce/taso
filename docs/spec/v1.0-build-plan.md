# Taso — spec v1.0 (build plan)

*Taso (Finnish: level). A level you can always step up from.*
*A storage substrate that makes cross-stream recovery boundaries, lineage, and trust promotion explicit primitives for agentic workloads. None of the mechanisms are new. The arrangement is.*

Status: **frozen for implementation.** Supersedes v0.2–v0.4. This is the document the implementation project starts from. Design history and evidence are in the earlier versions and the research report; they are not repeated here.

What changed from v0.4: runtime target is **runc + ZFS** for Phase 1, sandbox runtimes are Phase 3 behind the same Field API; **SQLite is a normal file in Phase 1 and is removed in Phase 2** by a Chronicle-native state store; **going deeper (a Chronicle-native filesystem) is Phase 4 and is gated**, not assumed; **Template(0) genesis is specified** (§4), it was missing.

---

## 0. One paragraph

A **Template** is an immutable, content-addressed base, born only by **sanction**. A **Vessel** is a workspace forked from a Template. Every durable change leaves the Vessel only as records in a single-writer **Chronicle** owned by a **Warden** the agent cannot write to. The Chronicle has state streams (cut by **Seals**, revertible) and an **effect ledger** (never revertible). An external effect fires only after its **intent** is durable; every irreversible intent is a **barrier** that fork, revert and rebirth must reconcile. **Navigator** reports whether a resume point is consistent with recorded evidence; safety is enforced at the point of use. A **policy engine** outside the Field decides what becomes the next Template. Everything unsanctioned is **purged**; the ledger and `ctl` are not.

## 1. Phases and gates

Each phase has an entry gate (what must be true to start) and an exit gate (what must be measured to finish). No phase starts on belief.

| Phase | Builds | Entry gate | Exit gate |
|---|---|---|---|
| **P0 — Invariants** | In-memory model: Chronicle, coordinator, two Wardens, one adapter, fake provider. Property tests with crash injection. | none | Zero duplicate provider effects across 10k randomized crash schedules; both reviewer interleavings pass; Navigator never returns `Consistent([])` where a duplicate is possible |
| **P1 — Phase 1 runtime: runc + ZFS** | Warden daemon; Field as a per-Vessel Unix socket in a per-Vessel namespace; ZFS dataset per Vessel; snapshot = Seal; `zfs send -i` → Garage = `fs` stream; coordinator (single-node `redb`, fsync). SQLite is a normal file on the dataset. | P0 passes | Hermes `state.db` at p64: 0 SIGBUS over 10 runs; p95 write latency ≤ 1.5× bare local NVMe (row A runc: 404k ops/s baseline); Seal p95 < 50 ms at p64 |
| **P2 — Rebirth** | `zfs receive` restore on another node from Template + last Seal + prefix; sealed-prefix ownership transfer; ledger reconciliation before effect authority. | P1 passes | SIGKILL the Warden 20×: reborn on node B < 30 s p95; dataset byte-identical to last Seal; old Warden refused 20/20; ledger tail intact; partial groups reported in `ctl` |
| **P3 — Seals + ledger in anger** | Turn-aligned sealing with durable bit; adapters for Hermes's real tools (mail, HTTP, git push); Navigator; the *Safe to Resume?* attacks + both reviewers' traces. | P2 passes | All attacks refused or reconciled; zero duplicate effects; **finding** recorded: fraction of Hermes turns with no durable record |
| **P4 — Sanction loop + Template genesis** | Policy engine (TOML rules, Cedar-ready), verifier Vessels, Candidate, partial promotion, Template(0) genesis tool (§4). | P3 passes | 10 Vessels from T(0); 1 auto-sanctioned after verifier; T(1) excludes all Scratch; 9 purged at TTL; `ctl` reconstructs the decision |
| **Phase 2 — Remove SQLite** | `taso-store`: a Chronicle-native state store (§5). Hermes's state moves to it. | P4 passes **and** the `db`-special-casing cost is measured (how much of the Warden exists only because SQLite is a file) | Hermes runs on `taso-store` with no SQLite on the dataset; Seal needs no transaction-quiescence check; P1–P3 gates re-pass |
| **Phase 3 — Sandbox runtimes** | gVisor and/or Firecracker behind the unchanged Field API. | A threat-model decision that OCI-class isolation is insufficient for the deployment | P1–P3 gates re-pass under the sandbox; the Sentry tax measured and accepted |
| **Phase 4 — Go deeper** | A Chronicle-native filesystem: the write path *is* the append; Seal is an LSN; the `fs` stream and the layer stack collapse into one structure. | **Gated, see §6.** Started only when §6's three conditions are met. | Fork < 1 ms; Seal is a pointer write; no shipper, no snapshot tool, no group markers |

Phases 2–4 are not promises. They are the order in which Taso goes deeper **when the evidence says it can**.

## 3. Phase 1 architecture (what gets built first)

```
                 ┌─────────── node ───────────┐
                 │  Vessel (runc container)    │
                 │   agent · tools · files     │
                 │   dataset: tank/vessel/<id> │
                 │        │ Field socket        │
                 │  ┌─────▼──────────────────┐ │
                 │  │ Warden                  │ │
                 │  │  seal = zfs snapshot    │ │
                 │  │  fs stream = zfs send -i│ │
                 │  │  ledger · ctl · groups  │ │
                 │  │  adapters (egress)      │ │
                 │  └─────┬──────────────────┘ │
                 └────────┼─────────────────────┘
                          ▼
          Garage (S3) ◄── segments, snapshots, Templates
          Coordinator ◄── ownership {epoch, holder, sealed_prefix}, anchored head
          Policy engine ── reads Candidates, writes sanction to ctl, births Templates
```

Rules specific to Phase 1:
- **Isolation is OCI-class** and the spec says so: user namespace, seccomp profile, Landlock on the dataset path, network namespace whose only route is the adapter socket, no credentials in the container. Accepted for the pilot's threat model; Phase 3 exists for when it is not.
- **ZFS is the layer stack.** `zfs clone` is fork; `zfs snapshot` is Seal; `zfs rollback` is revert (gated by Navigator); `zfs send -i` is the `fs` stream; `zfs receive` is rebirth. The Warden never implements CoW itself. Btrfs is the fallback if ZFS on the Hetzner kernel is a problem; the Field API does not change.
- **SQLite is a normal file.** No VFS shim, no `db` stream. A Seal is taken only at a turn boundary where the harness reports no open transaction; the Warden verifies by checking that no `-wal` has grown since the harness's quiescence signal. This is the one place Phase 1 knows SQLite exists, and Phase 2 deletes it.
- **Groups** apply to the `fs` stream only: a group is the set of writes between two Seals; it is committed by the Seal. Causal closure is trivial in Phase 1 because there is one state stream.
- **Field = socket, not filesystem relay.** The agent gets a POSIX filesystem (its dataset) and a socket for effects. Nothing else crosses.

## 4. Template(0) — genesis (previously missing)

A Template must exist before the first Vessel. Genesis is the one operation that creates a Template without a Candidate, and it is treated as the most sensitive operation in the system.

**Inputs.**
1. A source: an OCI image reference, or a directory tree, or an existing ZFS snapshot.
2. A **classification map**: globs → `PathClass` (`Source | Config | Hook | Secret | Scratch | Artifact`). Required; genesis refuses without one. Unmapped paths are `Unknown`.
3. A **policy** (the TOML in v0.3 §9.4, or a successor) whose hash is recorded.
4. An **actor**: a human or a named operator identity. Never a Vessel.

**Procedure.**
1. Materialize the source into a ZFS dataset `tank/template/<tmp>`.
2. Apply the classification map; refuse genesis if any path is classified `Secret` (secrets never enter a Template, including the first one) or `Hook` unless the actor explicitly waives with a reason recorded in `ctl`.
3. Content-address every file (BLAKE3, whole-file) into the Template manifest.
4. `zfs snapshot` the dataset; set it read-only; this snapshot is `Template(0).layer`.
5. Write the manifest: `{ id, parent: None, born_from: None, layers, classification_map, policy_hash, sanctioned_by: actor, ledger_pos: 0, created_at }`.
6. Write `ctl: genesis { template_id, actor, source, waivers }`. This is the first record of the Chronicle for the Template's lineage root.
7. Push the snapshot and manifest to Garage under the Template id.

**Invariants.**
- Exactly one `parent: None` Template per lineage root. A second genesis is a second root, not an update.
- Genesis is never automatic. There is no path from a Candidate to `parent: None`.
- The classification map is part of the manifest and is therefore itself sanctioned on every later Template; changing it is a sanction, not an edit.

**Tooling.** `taso template genesis --from oci://… --classify ./classify.toml --policy ./policy.toml --actor jarmo` in `taso-warden`. The "standard template setup" is this command plus a checked-in `classify.toml` and `policy.toml` for Hermes.

## 5. Phase 2 — removing SQLite (`taso-store`)

**Why.** SQLite is the only reason Phase 1 has a quiescence check, a `-wal` watch, and a transaction-aware seal rule. It is a file pretending to be a database, and Taso has to pretend along. A state store that is *born* in the Chronicle has none of that: a transaction is a group, commit is an append, Seal is any LSN, and there is nothing to ship because the store's log *is* the stream.

**What it is.** A small, embedded, single-writer record store for the agent's own state (session, tool results, memory index — whatever Hermes keeps in `state.db` today), with:
- a log-structured write path whose records are Chronicle records (stream `state`), so the Warden owns durability and there is no second log;
- read structures (an LSM or a CoW B-tree) rebuilt from the log on open, cached on the dataset, never authoritative;
- transactions = groups with commit markers, exactly the v0.4 `Group`;
- fork = open the same log at a parent Seal's LSN with a new tail; nothing is copied;
- a query surface deliberately smaller than SQL: key/value with ordered scans and secondary indexes declared at open. If Hermes needs SQL, this phase is wrong and the measurement in the entry gate will say so.

**Candidates to build on, in order of preference:** `fjall` (LSM, Rust, active) or `redb` (CoW B-tree with savepoints) as the read structure under a Chronicle-fed write path; `SlateDB` if object-storage-first turns out to matter more than local latency. Not `sled`. Not a new LSM from scratch.

**Entry gate (measured, not felt).** After P4: count lines and branches in the Warden that exist only because SQLite is a file; measure Seal latency attributable to the quiescence check; measure how often Hermes's turn boundaries are not quiescent. If all three are small, Phase 2 waits. If any is large, Phase 2 starts.

**Exit gate.** Hermes runs with no SQLite on the dataset; Seal has no database-specific rule; P1–P3 gates re-pass; fork of a Vessel with 1 GB of state takes the same time as fork of an empty one.

## 6. Phase 4 — going deeper, and the gate for it

The deep move is a Chronicle-native filesystem: the Vessel's write path *is* the Chronicle append; the layer stack, the `fs` stream and the snapshot tool collapse into one log; Seal is an LSN; fork is a pointer. In gVisor this is a Sentry `fsimpl` module (Go, a few thousand lines, precedent in tmpfs/overlay). On bare Linux it is a FUSE or kernel filesystem and considerably harder, which is why Phase 4 follows Phase 3.

**Taso goes deeper only when all three hold:**
1. **ZFS is the measured bottleneck.** Seal or fork p95 on ZFS exceeds the budget a real workload needs (budget set by P3's measurement of Hermes turn cadence, not by taste), *or* `zfs send -i` cost dominates Warden CPU at target concurrency.
2. **The ancestor has been validated.** DeltaFS (DeltaBox) or NILFS2 has been run on the pilot cluster and its numbers reproduced or refuted. Taso does not write a filesystem to find out whether log-structured CoW works; that is known. It writes one only if the existing ones cannot be made to speak Chronicle.
3. **Phase 2 is done.** With SQLite gone, the filesystem has exactly one job: files. A Chronicle-native filesystem that still has to special-case a database has not earned its complexity.

If any condition fails, Phase 4 stays closed and ZFS remains the layer stack. That is a success, not a deferral: the structure was the point.

## 7. Negative space (frozen)
1. No lock manager. 2. No host-side file handle to Vessel data. 3. No payload parsing. 4. No multi-writer state, no RWX volume, no shared POSIX between Vessels. 5. No automatic trust. 6. No self-sanction. 7. No purge of ledger or `ctl` within audit retention. 8. No zero-RPO promise for state. 9. No in-place base; no automatic genesis. 10. No rollback of the effect ledger. 11. No dispatch without durable intent. 12. No effect authority under `Insufficient`. 13. No process-memory recovery. 14. **No new filesystem, database, consensus or hash before its gate says so.**

## 8. Crates (Phase 1)

```
taso-core     envelope, chronicle, group, seal, lineage, ledger (intent/outcome/barrier/obligation),
              navigator, policy, template — pure, no I/O, fully property-tested in P0
taso-field    the Vessel side: socket client, adapter trait, fake provider for tests
taso-warden   the daemon: ZFS driver, Garage backend, coordinator, rebirth, purge, genesis CLI
```
Phase 2 adds `taso-store`. Phase 3 adds nothing (Field implementations live in `taso-field` behind a feature flag). Phase 4 adds `taso-fs` if and only if §6 opens.

## 9. First week

1. `cargo new --lib taso-core`; write the `ChronicleRecord`, `Group`, `Intent`, `Outcome`, `Seal` types and the hash chain.
2. Write the in-memory model and the first property test: two Wardens, one coordinator, sealed-prefix transfer, the old-Warden-CAS-after-transfer interleaving. Make it fail. Make it pass.
3. Write the adapter + fake provider model and the mail-duplication crash trace. Make it fail. Make it pass.
4. Write the Navigator over the model; label the first ten Chronicles by hand.
5. Only then: `zfs snapshot` from Rust on one Hetzner node.

The Omnissiah is served by tests that fail first.
